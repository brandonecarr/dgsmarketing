# Database migrations

Two layers, applied in order:

## 1. Bootstrap — `0000_stale_imperial_guard.sql`

Every enum + table + index + foreign key. Generated by `drizzle-kit generate`
from `src/schema/*.ts`. Run this first on a fresh Supabase project.

## 2. Hand-written follow-ups — `sql/0001_*.sql` → `sql/0020_*.sql`

RLS policies, trigram + tsvector indexes, the `is_tenant_member()` helper,
storage bucket bootstrapping, and per-phase additions. Apply **in numeric
order** after the bootstrap.

## Apply against Supabase

### Easiest path (Supabase SQL editor, one paste per file):

1. Open Supabase → SQL editor → New query
2. Paste `0000_stale_imperial_guard.sql`, run.
3. Then paste each file under `sql/` in numeric order (0001 → 0020), running
   each one before moving to the next.

### CLI path (`psql`):

```bash
export DIRECT_URL="postgresql://postgres:...@db.<project>.supabase.co:5432/postgres"

psql "$DIRECT_URL" -f packages/db/migrations/0000_stale_imperial_guard.sql

for f in packages/db/migrations/sql/*.sql; do
  echo ">> $f"
  psql "$DIRECT_URL" -f "$f" || break
done
```

### Drizzle path (regenerates from schema):

```bash
DIRECT_URL=... pnpm --filter @rosie/db push    # creates tables only
# then apply sql/*.sql manually as above
```

## After every schema change

1. Edit the relevant `src/schema/*.ts` file.
2. `DATABASE_URL=... pnpm --filter @rosie/db generate` — drops a new
   `NNNN_*.sql` file under `migrations/`.
3. Apply it via your usual path. The hand-written `sql/` follow-ups stay as-is
   unless the change affects them.
